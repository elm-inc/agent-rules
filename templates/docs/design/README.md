# Design

設計・実装方針のドキュメント。ADR とは異なり「これから何をどう作るか」「実装にあたっての方針」を扱う。

## 想定するファイル

| ファイル | 内容 |
|---|---|
| `implementation-plan.md` | モジュール構成、アーキテクチャパターン、実装順序 |
| `<機能名>-spec.md` | 個別機能の詳細設計 |
| `api-spec.md` | API 設計 (必要に応じて) |

## 受け入れ基準 (spec-driven, ADR-0006)

各 spec / implementation-plan には「完了の定義」を**検証可能な箇条書き**で必ず書く。これを実装の「契約」とし、実装後にこの基準への**適合性 (conformance)** を確認することで、出力が意図からズレる prompt drift を防ぐ。

- **機能要件**: 「X を入力すると Y を返す」など観測可能な振る舞いで書く (曖昧な形容詞を避ける)
- **制約**: 互換性・性能・セキュリティ・「既存テストを壊さない」等
- **非対象 (out of scope)**: やらないことを明示し、スコープの膨張を防ぐ

実装フロー: 仕様起草 → `/deepseek-redteam` で盲点レビュー → 実装 → **マージ前に `/gemini-review` で「受け入れ基準と ADR 制約への適合」を確認**。

> これは Claude Code 公式の **Outcomes-driven validation**（ルーブリックを書き、エージェントが完遂、採点エージェントが評価）と同じ思想。Managed Agents (CMA) を使う場面では、この受け入れ基準をルーブリックとして渡し採点させる。

## ADR との違い

- **ADR**: 過去に下した**決定の理由**を残す (immutable, 履歴として残る)
- **design**: 現在の**設計・方針**を表現する (随時更新)

`docs/design/` のドキュメントが古くなったら **直接書き換える**。歴史的経緯を残したい部分は ADR を新規作成。
