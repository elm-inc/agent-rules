# Stage 1 実証: Issue #40 (argv への API キー露出)

ADR-0020 の **Stage 1 (評価関数の敵対的検証)** を実タスクで初めて回した記録。
**本実験の成果物は「#40 の修正」ではなく「採点関数が信用できるかの判定」である。**

- 実施日: 2026-09-06
- 題材: [Issue #40](https://github.com/elm-inc/agent-rules/issues/40)
- 根拠: [ADR-0020](../../docs/adr/0020-parallel-exploration-and-scoring-oracle.md) /
  [設計](../../docs/design/parallel-exploration.md)

## なぜこの題材か

- 受け入れ条件が**完全に機械的**: 実行中プロセスの argv に秘密が出るか否か
- **実装アプローチが複数実在**: `curl --config -` / `x-goog-api-key` ヘッダ / netrc
- 意見ではなく**機構**で判定できる (ADR-0020 決定 3)

## 構成

```
sealed/                  ← 採点資産 (アームから書き換えさせない想定)
  score.sh               ← 受け入れ基準 → JSON スコア
  observe_argv.py        ← execve をトレースして argv を決定論的に捕捉
  capture_server.py      ← ダミー API。機能が生きているかを実測する
arms/
  good, good-goog        ← 正しい修正 (--config - / x-goog-api-key)
  bad-plain, bad-url     ← 既知の悪い実装 (現状のコード / URL 埋め込み)
  adv-noop               ← 【攻略】API 呼び出しを丸ごと消す
  adv-fast               ← 【攻略】即終了して観測窓を潰す
  adv-decoy              ← 【攻略】ダミートークンで検知をずらす
```

## 最重要の発見: 最初の採点関数は【本物のバグを 100 点にした】

初版の `observe_argv.py` は `/proc/<pid>/cmdline` を 5ms 間隔でポーリングしていた。結果:

| アーム | 初版スコア | 判定 |
|---|---|---|
| **bad-plain (未修正コードそのもの)** | **100.0** (`leaked=False`) | ❌ **本物のバグを満点にした** |
| good | 100.0 | 区別できていない |

原因を実測したところ、**197 回ポーリングして `curl` を 1 度も観測できなかった**。
短命プロセスに対してサンプリングは原理的に無力で、
「観測できなかった」が「漏れていない」として集計されていた。

→ `strace -f -e trace=execve` で **exec の瞬間に argv を捕捉**する決定論的方式へ作り替えた。
`ptrace_scope=1` でも自分で起動した子孫は追えるため制約にならない。

## 修正後の結果

| アーム | score | leaked | functional | 判定 |
|---|---|---|---|---|
| good | **100.0** | false | true | ✅ 正しい修正が最上位 |
| good-goog | **100.0** | false | true | ✅ |
| bad-plain | 50.0 | **true** | true | ✅ 漏洩を検出 (初版は 100 だった) |
| bad-url | 0.0 | true | false | ✅ URL 埋め込みを検出 |
| adv-noop | 20.0 | false | **false** | ✅ 攻略失敗 (呼び出しを消すと機能が 0) |
| adv-fast | 50.0 | **true** | true | ✅ 攻略失敗 (exec 捕捉は速度で回避できない) |
| adv-decoy | 0.0 | **true** | false | ✅ 攻略失敗 |

## Stage 1 合否 (ADR-0020 決定 2)

| 条件 | 結果 |
|---|---|
| 既知の悪い実装が全て下位に落ちる | ✅ bad-plain 50 / bad-url 0 < good 100 |
| **敵対的エージェント 2 個以上が上位に入らない** | ✅ 3 個とも最上位に届かず (20 / 50 / 0) |
| 採点の再現性 (3 回一致) | ✅ good=100×3, bad-plain=50×3, adv-fast=50×3 |
| 測れない指標を 0 で埋めない (決定 7) | ✅ strace 不在時に `score=null, measurable=false` |
| 採点資産がアームから書き込み不能 (決定 6) | ⚠️ **未検証** (下記) |
| `/mutation-check` 生存変異率 ≤10% | ⚠️ **本題材では非適用** (下記) |

### 未検証・非適用の項目 (正直に記録する)

- **封印 (決定 6) は実証していない。** 本実験の `arms/` は人手で書いたシェルスクリプトであり、
  自律エージェントが `sealed/` を書き換えようとする状況を再現していない。
  同一ツリーに置いているだけで、read-only マウントや別チェックアウトによる強制はしていない。
  **Stage 2 に進む前にここを実装・検証する必要がある。**
- **`/mutation-check` は本題材に適用できない。** あれはテストスイートの検出力を測る道具で、
  本実験の採点対象は「プロセスの観測結果」であってテストスイートではない。
  代わりに**敵対的アームによる直接検証**を行った (こちらの方が強い検証である)。
  ADR-0020 の合格条件は題材の性質に応じて読み替える必要がある。

## 結論

**この題材に限り、採点関数は信用できる状態になった。** ただし最も価値のある成果は次の点:

> **Stage 1 の関門は実際に機能した。** 初版の採点関数は本物のバグを満点にしており、
> これを持って Stage 2 (N 並列) に進んでいたら、**未修正コードが 1 位タイで選ばれていた**。
> 「採点関数を書いた」だけで先に進むのが危険であることが、初回の実証で裏付けられた。

この経験は ADR-0020 決定 2 の「敵対的ゲートを必須にする」判断そのものを支持する。
