# 独立競合探索 (N 案並列 + 機械選抜) の設計

- ADR: [0020-parallel-exploration-and-scoring-oracle](../adr/0020-parallel-exploration-and-scoring-oracle.md)
- 制定日: 2026-09-06
- 状態: **起草。Stage 1 の実証待ち**

## 1. 背景・目的

モデル能力が上がった結果、**人間 1 人が critical path に居座ること**が生産性の律速になった。
以前は A/B の 2 案しか試せなかったものが、いまは 10 案試しても作業コストが大きく変わらない。
にもかかわらず「依頼 → 待つ → レビュー → 指示」のループが人間を毎周回で消費している。

人間がやっている仕事を分解すると 3 つある:

| 仕事 | AI に渡せるか |
|---|---|
| **何が「良い」かを定義する** | ❌ 渡せない。これが本質的に人間の仕事 |
| **良いかどうかを判定する** | ⚠️ 条件付き。§2 の制約に従う |
| **判定を受けて次を指示する** | ✅ 渡せる。**ここが今 critical path を作っている** |

本設計の目的は 3 番目を critical path から外すことであり、そのために 1 番目を
**実行可能な形に落とす**ことを最優先の前提条件として置く。

## 2. 決定的な制約: 検証は並列化できない

設計の形を規定する制約なので最初に置く。

> **9 個の審査 LLM の実効独立票は約 2。最良の単一審査者がパネル全体と同等かそれ以上。**
> 審査者を増やしても集約アルゴリズムを賢くしても直らない (既存手法はギャップの最大 11% しか埋めない)。
> ボトルネックは集約方法ではなく**審査者同士の相関**。
> — [Nine Judges, Two Effective Votes: Correlated Errors Undermine LLM Evaluation Panels](https://arxiv.org/abs/2605.29800)
>   (2026-05 / [Apple ML Research](https://machinelearning.apple.com/research/correlated-llm-evaluation-panels))
>   7 モデルファミリー・9 LLM・3 データセット。Kish effective sample size と Condorcet null model で定量化。
>   prompt 変種・temperature・CoT・pairwise preference (RewardBench) でも頑健。

したがって:

- **生成側 (N 案を作る) は並列化が効く**
- **検証側 (どれが良いか決める) は「数」では強くならない**。強くなるのは**機構の異種性**のみ

これは本リポジトリの実測と一致する ([ai-workflow.md §4-1](ai-workflow.md)):
仕込みバグ 6 件に対し **linter 3/6・LLM 5/6・和集合 6/6**。和集合が効いたのは意見が 2 つあったからではなく、
**静的解析と意味推論という別種の機構**だったから。ruff は「ファイル未 close」を数ミリ秒で取り、LLM は 6/6 見逃した。

ADR-0017 の「多様性はハーネスでは買えない」「異ベンダーは常時 1 つまで」は、この論文が出る前に
同じ結論へ到達していた。本設計はそれを**撤回せず強化する**。

## 3. レバレッジ点: 評価関数 (scoring oracle)

[AlphaEvolve](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)
(FunSearch の一般化) は **LLM + 自動評価器 + 進化ループ**で行列乗算アルゴリズムの改善や
データセンター最適化を出した。繰り返し指摘されているのは**評価器の品質が成否を決める**という点。

本リポジトリの現状の穴:

> `templates/docs/design/README.md` の受け入れ基準は**散文**で、適合判定は `/gemini-review` = **LLM 判定**。
> N=2 なら人が読める。**N=10 を機械的に順位付けするには実行可能な採点関数が要る。**

そして本リポジトリは既に「**評価器を評価する道具**」を持っている:

> `/mutation-check` は「テストが本当にバグを catch できるか」を変異注入で測る。
> これを一般化すると「**採点関数は良い案と悪い案を区別できるか**」の測定になる。
> **意見ではなく機構で検証している**ため、§2 の相関誤りの罠に落ちない。

## 4. 段階的な導入 (順序が本質)

### Stage 1: 受け入れ基準を実行可能にし、攻略耐性を確認する 【最優先・関門】

**採点関数を書くだけでは足りない。** 強い最適化圧 (N 並列 + 自律ループ) の下では、
得られるのは「最良の実装」ではなく「**採点関数を最も上手く攻略した実装**」になる。
しかも Stage 4 で人間が上位数件しか読まないなら、攻略成功案は回収されない。
したがって Stage 1 は 3 つの部品からなる。

#### 1-a. 採点対象を封印する (tamper resistance)

**採点に使うテスト・ベンチはアームの作業ツリーから取らない。**
アームがテストを弱める・`# noqa` を足す・ベンチ対象を縮小する、といった攻撃を構造的に潰す。

```
sealed/                  ← 封印された採点資産。アームからは read-only
  tests/                 ← 受け入れテスト (アームは変更できない)
  bench.sh               ← ベンチ (対象と入力を固定)
  score.sh               ← 採点ロジック
arms/<n>/                ← 各アームの worktree。ここだけ書き込み可
```

採点は**アームの外のプロセス**が、`sealed/` のテストを `arms/<n>/` の実装に対して実行する。
アームが `sealed/` に書けないことは権限で保証する (worktree 分離 + 読み取り専用マウント/別チェックアウト)。

> **「採点ロジックを隠す」ことは諦める。** 同一リポジトリに置く限り
> `cat` / `git show HEAD:<path>` / `git grep` のいずれかで読めるため、隠蔽は成立しない
> (2026-09-06 に実証)。Read 権限を path で拒否しても Bash 経由で漏れる。
> **秘匿ではなく改変不能性で守る。**

#### 1-b. 測れないものを 0 にしない

採点スクリプトは `|| echo 0` のようなフォールバックを**書いてはいけない**。
ツール未導入・一時障害・flaky を「実力が低い」に変換してしまい、
**環境運が良かったアームが上位に来る**。これは ADR-0019 の
「測れないものを 0 と偽らない」に真正面から反する。

```bash
#!/usr/bin/env bash
# sealed/score.sh — 受け入れ基準を機械可読なスコアに落とす。
# 出力: {"score": <数値|null>, "measurable": <bool>, "detail": {...}, "missing": [...]}
# 測れなかった指標は null にし、measurable=false にする。**0 で埋めない。**
set -uo pipefail
missing=(); 
run() { # run <name> <cmd...> → 成功なら値、失敗なら空
  local n="$1"; shift
  if v="$("$@" 2>/dev/null)"; then printf '%s' "$v"; else missing+=("$n"); printf ''; fi
}
passed=$(run passed  bash -c "pytest -q --json-report --json-report-file=/dev/stdout | jq -r '.summary.passed'")
cov=$(   run cov     coverage report --format=total)
lint=$(  run lint    bash -c "ruff check --output-format=json . | jq 'length'")
p95=$(   run p95     bash bench.sh --p95-ms)

python3 - "$passed" "$cov" "$lint" "$p95" "${missing[@]:-}" <<'PY'
import json,sys
passed,cov,lint,p95,*missing = sys.argv[1:]
missing=[m for m in missing if m]
vals={"passed":passed,"coverage":cov,"lint":lint,"p95_ms":p95}
if missing:
    print(json.dumps({"score":None,"measurable":False,"detail":vals,"missing":missing})); raise SystemExit
p,c,l,q=float(passed),float(cov),float(lint),float(p95)
score=min(100, p*2 + c*0.3 - l*0.5 - max(0,(q-100))*0.1)
print(json.dumps({"score":round(score,1),"measurable":True,"detail":vals,"missing":[]}))
PY
```

**`measurable: false` のアームは順位から除外し、失格ではなく「測定不能」として人間に報告する。**

#### 1-c. 敵対的ゲート (これが本体)

「既知の悪い実装 2〜3 個を下位に落とせるか」は**固定サンプルへの識別力**でしかなく、
最適化圧に対する頑健性を測っていない。Stage 2 に進む条件は次とする:

> **採点関数を攻略しようとする専用エージェントを複数走らせ、
> 「問題を解かずにスコアだけ上げた実装」が上位に入らないこと。**

攻略側に明示的に許す手口 (これらが効いたら採点関数は不合格):
assert の無いテストを増やす / 実行するだけでカバレッジを稼ぐ / `# noqa`・lint 除外設定を足す /
ベンチ対象を小さくする・キャッシュに当てる / テストを削る・弱める。

**1-a の封印が効いていれば後半 3 つは構造的に不可能になる。**
それでも通る攻略が見つかったら、採点関数か封印のどちらかに穴がある。

#### Stage 1 の合否 (数値で決める)

| 項目 | 合格条件 |
|---|---|
| 既知の悪い実装 (2〜3 個) | 全て下位に落ちる |
| **敵対的エージェント (2 個以上)** | **上位に 1 つも入らない** |
| `/mutation-check` の生存変異率 | **10% 以下** (`--threshold 90` 相当) |
| 採点の再現性 | 同一実装を 3 回採点してスコアが一致する |

**1 つでも満たさなければ Stage 2 に進まない。** 「だいたい動くから通す」を許さないために
閾値を数値で固定する。

### Stage 2: 生成側を扇形に広げる

Workflow (決定論的ファンアウト) を使う。実測された制約:

| 項目 | 値 |
|---|---|
| 同時実行 | 最大 16 (CPU 数依存) |
| 1 run の総エージェント | 1,000 |
| `parallel()`/`pipeline()` の要素上限 | 4,096 |
| コスト警告 | 25 agents または 1.5M tokens 超で advisory |
| 途中介入 | **不可** (unattended 前提。承認ゲートが要るなら phase を別 workflow に分ける) |

**アームの分散は seed ではなく approach で行う。**
同じモデル・同じプロンプトの seed 違いは相関して実効アーム数を減らす (§2 と同じ理屈)。
分散させるべき軸: アルゴリズム / ライブラリ / データ構造 / 制約の緩め方 / 責務分割。
**この「10 通りの攻め方を設計する」こと自体を委譲してよい** (`/fable-task` の使いどころ)。

> ⚠️ **「approach 分散」は主観的なので、事後に測って検証する。**
> そう名乗るだけで N を増やす抜け道になりうる (レッドチーム指摘)。
> アーム間の成果物の類似度 (差分の Jaccard 係数など) を測り、
> **中央値が 0.7 を超えたら「実質は同一アプローチ」とみなして N を減らす**。
> 独立競合探索を名乗る条件 (ADR-0020 決定 1) の**測定可能な判定基準**をここに置く。

> ⚠️ **性能指標は並列実行で汚染される。** N アームを同時にベンチすると CPU/IO を奪い合い、
> `p95` の意味が壊れる。worktree 分離はファイルしか分けない。
> **性能を採点に含める場合、そのフェーズだけは直列化する**か、専用ポート・専用 DB・
> 専用一時領域を割り当てる。共有資源 (ポート・DB・キャッシュ) の衝突は `/ports` で事前確認する。

### Stage 3: 非同期で走らせ続ける

| 手段 | 実行場所 | マシン電源 | 最小間隔 | 用途 |
|---|---|---|---|---|
| `claude --bg` / `claude agents` | ローカル | 必要 | — | 作業中の並行タスク |
| `/loop` | ローカル | 必要 | 1 分 (7 日で失効) | 短期の監視ループ |
| **Routines (`/schedule`)** | **クラウド** | **不要** | 1 時間 | **不在時の本命** |

Routines は GitHub イベント・API POST でも起動でき、Slack / Linear connector が使える。
「寝ている間に N アーム走らせ、朝に採点済みの順位表を見る」はここで実現する。

### Stage 4: 人間の注意をバッチ化する

タスクごとの割り込みを**決定キュー**に変える。`/status` を拡張し、AI が判断を求める項目を
**根拠と採点結果を添えて**一箇所に溜める。人間は差分ではなく**決定**をレビューする。
これが §1 の「3 番目の仕事」を critical path から外す実体。

### Stage 5: 較正台帳 (ただし軽く作る)

どのレビュー層が実際に何を捕まえたかを記録する。本リポジトリは既にこの習慣がある (§4-1 の実測)。

> **重み付けアルゴリズムは作り込まない。** Metaculus は track record 重み付け (Metaculus Prediction) を
> **2024-11 に廃止**し、現在は**単純な recency-weighted median** を使っている
> ([Metaculus FAQ](https://www.metaculus.com/faq/) で確認済み)。
> 廃止版は performance weighting + extremization を掛けていた。
> なお「Brier 0.107 vs 単純 median 0.108 でほぼ差が無かった」という具体値は
> [二次情報](https://forum.nunosempere.com/posts/acREnv2Z5h4Fr5NWz/my-current-best-guess-on-how-to-aggregate-forecasts)
> であり未検証。**判断の根拠は「Metaculus 自身が精緻な重み付けをやめた」という事実に置く。**

「この層は最近何も捕まえていない」が見えれば十分で、それは**層を外す**判断材料になる
(ADR-0017 の「層を減らすほど各層が実行される」と整合)。

## 5. Metaculus から取るもの / 取らないもの

| 取る | 内容 |
|---|---|
| **事前登録された解決基準** | 予測が改善可能なのは集約が賢いからではなく、**いつ・何をもって決着とするかが事前に客観的に固定されている**から。並列探索では「走らせる前に採点方法を固定する」に対応する |
| **proper scoring rule の発想** | log score は真の信念を報告するのが最適戦略になる。採点関数も「正直な自己申告が最適」になる形にする |

| 取らない | 理由 |
|---|---|
| **精緻なキャリブレーション重み付け** | Metaculus 自身が廃止 (§4 Stage 5) |
| **多数決・集約** | 本件は集約ではなく**選抜**。採点関数で順位が付けば集約は不要。§2 より審査者を並べる行為自体が非効率 |

## 6. ガードレール (交渉の余地なし)

自律度を上げると失敗の**質**が変わる。公表事例:

| 事例 | 損害 | 原因 |
|---|---|---|
| LangChain 4 エージェントのループ | **$47,000** | 11 日間走行、誰も監視していなかった |
| DN42 スキャナ | **$6,531** | エラーのたび CloudFormation スタックを重複起動 |
| Step Finance (DeFi) | **$27-30M** | AI エージェントに**人間承認なしの送金権限**を与えていた |

さらに **silent failure**: 本番 8 週間の追跡で、壊れたコンポーネントが**自己申告では "operational"** と
報告する事象が記録されている ([arXiv 2606.14589](https://arxiv.org/pdf/2606.14589))。
HTTP 200 を返しながら誤答するため従来の監視に掛からない。reward hacking は
**15.4% の failure mode rate** として観測されている。

> 本リポジトリは既にこの原則を実装している。`frontier-usage.sh` は
> 「測れないものを $0 と偽らず `NA` / `?` で出す」「未計上を `+` で示す」(ADR-0019 §5)。
> **自律度を上げるなら、この原則を全計器へ広げる。**

必須のガードレール:

1. **自律実行には予算の hard cap を置く。** ADR-0010 の「ブロックしない人手ゲート」は
   **人間が起動する場合の規律**であり、無人実行では成立しない (ADR-0020 決定 4)
2. **worktree 分離を必須にする。** 並列アームが同じファイルを触ると上書きし合う
3. **`bypassPermissions` は「worktree の外に書けない・課金 API を叩けない・本番に触れない」タスクに限定する。**
   Step Finance はこの設計を誤った事例
4. **採点対象を封印する (隠すのではなく改変不能にする)。** 同一リポジトリでの秘匿は
   `cat` / `git show` / `git grep` で破れることを実証済み (§Stage 1-a)。
   守るべきは秘密性ではなく**アームが採点資産を書き換えられないこと**

## 7. 受け入れ基準

本設計が「機能した」と言える条件。**Stage 1 が満たせなければ Stage 2 以降に進まない。**

### Stage 1 (必須の関門・数値で判定する)
- [ ] `sealed/score.sh` が JSON を返し、**測れない指標を 0 で埋めず `measurable:false` にする**
- [ ] 採点資産 (`sealed/`) がアームから**書き込み不能**であることを確認した
- [ ] 既知の悪い実装 2〜3 個が全て下位に落ちた
- [ ] **敵対的エージェント 2 個以上が上位に 1 つも入らなかった**
- [ ] `/mutation-check` の生存変異率が **10% 以下**
- [ ] 同一実装を 3 回採点してスコアが一致した (再現性)

**検証手段**: 良い実装 1 + 悪い実装 3 + 攻略専用 2 の計 6 個を採点関数に通し、
順位・`measurable` フラグ・再現性を記録する。攻略側が上位に入ったら**採点関数の不合格**として
Stage 2 に進まない。

### Stage 2 以降 (Stage 1 通過後)
- [ ] 同一ゴールに対し approach を分散した N≥5 アームを Workflow で生成できた
- [ ] 採点関数で機械的に順位が付き、人間が読むのは上位 1〜2 件だけで済んだ
- [ ] アーム間の出力類似度を確認し、相関が高すぎないこと (approach 分散が効いていること)

**検証手段**: 1 回の実タスクで N アームを回し、`frontier-usage.sh` 相当でコストを記録。
人間が読んだ候補数を数える (2 件以下なら成功)。

### 全体
- [ ] 自律実行に hard cap が実装され、超過時に**実際に停止する**ことをテストで確認
- [ ] 並列アームが worktree で分離され、相互に上書きしないことを確認

## 8. 未解決 / 引き受けるリスク

- **採点関数を書けない種類のタスクがある** (UI の良さ、ドキュメントの分かりやすさ、設計の妥当性)。
  これらは Stage 1 を満たせないので**並列化の対象外**とし、従来どおり人間 + レビュー層で扱う。
  「何でも並列化できる」とは考えない
- **採点関数の設計コスト自体が高い場合、割に合わない。** 1 回きりのタスクでは
  採点関数を書く時間 > 10 案から選ぶ時間 になりうる。**反復するタスクに限定する**
- **Stage 1 の実証が失敗する可能性がある。** その場合「本リポジトリの仕事は並列探索に向かない」が
  結論になる。これも価値のある結果として受け入れる (ADR-0020 の帰結に記載)
- **スコアをアームに返すと oracle query として hill-climbing されうる。** 封印しても
  スコア値そのものが漏れれば試行錯誤で攻略できる。緩和として (a) アームにスコアを返さない
  (一発勝負にする)、(b) 返す場合は pass/fail だけにする、のいずれかを採る。
  **反復改善させたい場合は、この攻略リスクを引き受けていることを自覚する**
- **hard cap は請求を完全には止められない。** API 課金の反映には遅延があり、
  cap 到達後に停止しても実際の請求はさらに積まれうる。cap は「暴走を数時間で止める」装置であって
  「上限を保証する」装置ではない
- **採点関数のバージョン管理が要る。** 採点ロジックが変わると過去の順位と比較できず
  較正台帳が無意味になる。`sealed/` の変更は必ずコミットし、スコアに採点関数の commit を併記する
