# ADR-0010: Fable 5 従量課金移行に伴う活用・モニタリング規律

## ステータス

採択 (2026-07-01)

## 文脈

Claude Fable 5 は輸出管理指令で 2026-06-12 に全顧客で無効化されていたが、**利用再開**した。ただし **2026-07-07 以降は従量課金 (実費) に移行**すると通知されている。これにより Fable 委譲のコスト構造が変わる。

- **これまで**: Fable は Max プランのクォータを消費 (Opus の約 2 倍速く消費)。サブスク枠内なので「クォータが余っていれば念のため Fable」も許容余地があった。
- **7/7 以降**: $10/$50 per MTok が **実費 (ドル) として請求**される。過剰利用が直接コストになる。

一方で「高性能を活用したい」要求もあり、Fable を過度に絞ると価値を取り逃す。**厳選しつつ活用し、過剰利用を検知・抑制できる状態**が必要。

現状把握で分かったこと:

- Fable の使い分け基準 (`/fable-task` 4 カテゴリ / `/fable-review` 6 条件) は既に整備済みで妥当。ただし全体が「クォータ消費」前提で書かれ、各所に「2026-06-12〜 停止中 → Opus 4.8 代替」の暫定注記が残っていた。
- `scripts/track-cost.sh` は月次・手動で、**Claude/Fable のトークン集計は未実装 (TODO)**。シェル履歴ベースのスキル頻度集計は TUI 呼び出しを拾えない。→ **Fable の実費が見えていなかった**。
- Claude Code の transcript (`~/.claude/projects/**/*.jsonl`、サブエージェントログ含む) に **メッセージ単位で `model` と `usage` (input / cache write / cache read / output tokens) が記録**されている。→ ローカルで Fable だけ抽出し $ 換算する自動集計が可能。
- 検証で **2026-06 に `claude-fable-5` の利用が ~$595 分検出**された (6/10〜6/13、6/12 の停止で途切れる。複数プロジェクト横断)。**約 3 日で $595 = 予算 $100/月なら 1 日で超過する規模**。監視の必要性を裏付ける実データ。

## 決定

Fable を「厳選 (A) × 可視化 (B) × 人手ゲート (C)」で運用する。**ハードブロックはしない** (高性能活用と両立させる)。

- **A. タスク厳選**: 既存の委譲基準を維持しつつ、委譲時に「委譲理由」に加え **「なぜ Opus では不足か」を 1 行**明示する (実費を正当化する根拠)。**1 タスク 1 委譲** (往復＝追加実費) を徹底。`/fable-review` は日常差分に降ろさず「最後の砦」に限定。
- **B. 可視化**: `scripts/fable-usage.sh` が transcript から当月 Fable 実費を自動集計 ($ 換算)。**statusline に当月累計 $ を常時表示** (使っていない月は非表示)。`track-cost.sh` からも呼び出し月次レポートに組み込む。結果は `docs/design/ai-workflow.md §8` に転記。
- **C. 人手ゲート**: 月次予算 **$100/開発者1人** (`FABLE_BUDGET_USD` で調整) を基準に、超過後も委譲・レビューを止めはしないが **起動前に「本当に Fable が要るか」を都度確認する**運用に切り替える。statusline はしきい値で色が変わる (<70% 緑 / 70-99% 黄 / ≥100% 赤)。
- 暫定注記 (停止中 → Opus 代替) を CLAUDE.md・両スキルから除去し、`model: "fable"` に復帰。

単価: input $10 / output $50 per MTok は通知値。cache write/read は Anthropic 標準の write=1.25×・read=0.1× を input 単価に乗じた**推定** ($12.5 / $1 per MTok)。正確な請求額は Console が正。

## 理由

- **実費課金では「見えないもの」は制御できない**。ローカル transcript 集計なら Console のタイムラグ・手動確認を待たず、日次かつ per-model で把握できる。
- **可視化 (statusline 常時表示) が最も安価で効く制御**。目に入り続けることで、しきい値に達する前から自然に自制が働く。
- **ハードブロックにしない**理由: 予算超過を理由に、セキュリティ・課金・データ破壊に関わる最終レビュー (`/fable-review`) まで自動で止まると、コスト最適化のために品質ガードを外す本末転倒が起きる。「高性能を活用したい」要求とも両立しない。判断は人間に残す。
- 6 月の ~$595 実測が示す通り、Fable は容易に予算を突破し得るため、**厳選と計器はセットで必要**。

## 検討した代替案

### 代替案 A: しきい値超過でスキルを自動ブロック (ハードゲート)
- Pros: 過剰利用を機械的に防げる。事故防止は最も強い。
- Cons: 予算超過時にクリティカルな最終レビューまで止まる。高性能活用と相反。誤検知 (集計は推定) で必要な委譲を阻害。
- 不採用理由: 品質ガードをコスト都合で外すリスク。判断は人手に残す方が安全。

### 代替案 B: 可視化せず規律 (ドキュメント) だけで運用
- Pros: 実装ゼロ。
- 不採用理由: 実費が見えないと過剰利用に気づけない。6 月の $595 も事後に手で調べて初めて判明した。計器がないと規律は形骸化する。

### 代替案 C: Anthropic Console ダッシュボードに一本化
- Pros: 請求額として正確。実装不要。
- Cons: リアルタイムでない・手動確認・statusline に出せない。日々の自制には遅い。
- 不採用理由: ローカル transcript 集計を主計器にし、Console は突き合わせ用の正とする方が運用に乗る。

### 代替案 D: 難タスクは `/model fable` でセッションごと Fable 常用
- 不採用理由: セッション全体が実費になりコストが爆発。サブエージェント委譲で Fable 利用を局所化する既存方針 (ADR-0006) を維持。

## 帰結

### Pros
- Fable 実費が statusline で常時見え、予算に対する位置が一目で分かる。
- 過剰利用の芽 (往復委譲・安易な最終レビュー) を規律と計器の両輪で抑えつつ、高難度局面では厳選して活用できる。
- 6 月のような集中利用を事後でなく当月中に検知できる。

### Cons / 限界
- cache 単価は推定。正確な請求は Console 参照が必要 (ズレ得る)。
- 集計は **このマシンの transcript のみ**。複数マシンで開発する場合の合算は未対応 (将来課題)。
- statusline のリフレッシュはキャッシュ (既定 10 分) 経由なので、直近の委譲が即時には反映されない (裏で更新)。
- transcript のタイムスタンプ (UTC) とファイル mtime (ローカル) の月境界で数時間のズレが出得る (次回集計で自己補正)。

### 将来の検討事項
- 複数マシン集計 (transcript を集約 or Console API 連携)。
- 予算しきい値の実運用チューニング ($100 が妥当か 1-2 ヶ月で見直し)。
- Opus 側トークンの併記による Fable/Opus 比率の可視化。
