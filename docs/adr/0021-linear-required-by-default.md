# ADR-0021: Linear を既定必須にし、乖離を /status で検出する

## ステータス

採択 (2026-09-07)

## 文脈

複数プロジェクトで Linear の Issue / Project が取り残される、という課題が出た。
**推測で対策を作らないため、まず 15 リポジトリの実データを取った** (2026-09-07)。

| 指標 | 実測 |
|---|---|
| worktree タスク 145 件中の Linear 連携 | **39 件 (27%)** |
| commit メッセージへの `(ELM-xxx)` 参照 | **0 件** |
| docs 冒頭の `Linear: ELM-xxx` | **1 件** |

分布は極端だった:

| 運用されている | 運用されていない |
|---|---|
| 顧客案件 A: 22/22 | 自社ツール X: 0/19 |
| 顧客案件 B: 8/8 | 自社ツール Y: 0/12 |
| 自社プロダクト C: 4/6 | agent-rules: 5/52 |

**顧客案件はほぼ完全に運用され、自分のリポはほぼゼロ**という分かれ方をしている。

> 本 ADR では**リポジトリ名を伏せる**。agent-rules は public repo であり、
> 案件名を出さないという本 ADR 決定 2 の原則を、この文書自身にも適用する
> (起草時に実名で書いてしまい、レビューで気づいて修正した)。
> 実名を含む集計は `scripts/linear-audit.sh` をローカルで実行すれば得られる。

### 診断: 「メンテを忘れる」ではなく「作業経路の外にある」

- `/worktree-start` の `--linear` は**任意フラグ**。付けなければ Linear は最初から存在しない
- 一方 `/worktree-finish` は連携済みなら**自動で Done にする**。つまり**出口は既に自動**
- CLAUDE.md は「commit に `(ELM-123)`」と定めているのに**実績 0 件** = 規約が運用されていない

**穴は入口だけ**であり、規律を増やしても入口が任意である限り同じことが起きる。

## 決定

### 1. Linear は既定で必須にする (opt-in → opt-out の反転)

`/worktree-start` は**既定で Linear Issue を作り** In Progress に遷移させる。
`--linear <ID>` は「既存 Issue に紐付ける」指定に意味を変える (省略時は新規作成)。

### 2. 除外はリポジトリ自身が宣言する。中央集権リストは作らない

恒久的に Linear が不要なリポは、**自身のルートに `.no-linear`** を置く (1 行目に理由)。
1 回だけ外したいときは `--no-linear`。

> 🔒 **なぜ中央集権リストにしないか**: agent-rules は **public repo** であり、
> 除外リストには顧客案件のリポジトリ名が並ぶ。`/ports` の予約台帳を本リポに置かないのと
> 同じ理由 (ADR-0018) で、**案件名を public に出さない**。各リポが自分のことだけ宣言する。

### 3. 乖離は `/status` が毎回検査する

`scripts/linear-audit.sh` を新設し、`/status` の §3-c で毎セッション実行する。
ADR-0017 が `model-doctor --probe` を `/status` に組み込んだのと同じ手口
(**主経路をローカルに置き、目に入る場所で回す**)。

**検出するのは 3 つだけに絞る**:

| 検出項目 | 意味 |
|---|---|
| active なのに `linear_issue_id` が null | **入口をすり抜けた** |
| active のまま worktree ディレクトリが消えている | **出口を通っていない** → Issue が In Progress のまま残る |
| active で worktree はあるが長期間コミットが無い (既定 60 日) | **滞留** |

> **滞留検出は移行作業をやってみて初めて必要と分かった。**
> 未連携の active 8 件を調べたところ **6 件が 85-129 日停止**しており、うち 1 件は
> 未マージコミットが 0 (実質空) だった。ここに機械的に Issue を作れば、
> **避けたい滞留を自分で作ることになる**。「Issue を作る」前に「まだやるのか」を問える形にした。

**乖離ゼロなら無音**にする。毎回 20 件出るような一覧は読まれなくなり、計器としての価値を失う
(ADR-0019 で statusline に学んだのと同じ)。同じ理由で **1 タスク 1 行**にまとめる
(初版は同じタスクが複数行に散っていた)。

### 4. 検査不能を 0 件と誤認しない

`jq` 不在等で検査が成立しなかった場合は終了コード 2 を返し、`/status` は
「Linear 乖離を**検査できていない**」と注意に出す。ADR-0019 / ADR-0020 決定 7 の一貫適用。

## 理由

- **入口が任意である限り、規律をいくら書いても運用されない**。実測 27% / commit 参照 0 件が
  それを示している。構造を変えるのが先
- **出口は既に自動なので、入口さえ閉じれば大半は解決する**。作る仕組みを最小にできる
- **顧客案件は既に 100% 運用されている**。困っているのは自分のリポなので、
  既定必須にしても顧客案件側の運用は変わらない (追加の負担が生じない)
- **除外を各リポに置くことで、public repo への案件名混入を構造的に防げる**

## 検討した代替案

### 代替案 A: 案件種別で明示的に分ける (顧客案件のみ必須)
- Pros: 実測の分布に最も忠実。要らない場所に義務を課さない
- Cons: 「どちらか」の判断が新たに必要になり、判断漏れが新しい穴になる
- 不採用理由: ユーザー判断で「基本は必須・明示的に除外」を採用。
  **既定を安全側に倒し、外すときだけ意思表示させる**方が漏れにくい

### 代替案 B: 全リポで任意のまま、検出だけ入れる
- Cons: 検出しても入口が任意なら「毎回同じ乖離が出て無視される」状態になる
- 不採用理由: 計器だけ増やして規律が変わらない典型

### 代替案 C: 定期実行 (Routines) で棚卸しする
- Cons: 通知が流れると読まれなくなる。`/status` は**セッション開始時に必ず目に入る**
- 不採用理由: ADR-0017 が `--probe` で同じ判断をしている。整合を取る

### 代替案 D: commit メッセージの `(ELM-xxx)` を CI で強制する
- Cons: 実績 0 件の規約をいきなり CI で強制すると、全コミットが落ちて運用が止まる
- 不採用理由: 今回は入口と棚卸しに絞る。commit 規約は運用が定着してから再検討

## 帰結

### Pros
- 「付け忘れる」経路が構造的に消える
- 取り残された Issue (worktree が消えたのに In Progress) が毎セッション目に入る
- 除外の意思表示が各リポに残るため、後から「なぜ対象外か」を追える
- public repo に顧客案件名が混入しない

### Cons / 限界
- **既定必須にすると、Linear が不要なリポでも最初の 1 回は除外宣言が要る**。
  移行期は `.no-linear` を置く作業が発生する
- **Linear 側にしか無い情報は検出できない**。ローカルに痕跡が無い放置 Issue
  (worktree を作らずに Linear だけ立てた等) は `linear-audit.sh` の対象外。
  気になるときは `/linear-status` で Linear 側から見る
- **滞留の閾値 60 日は暫定**。`LINEAR_AUDIT_STALE_DAYS` で変えられるが、
  実運用でどの値が妥当かは未検証
- **Linear MCP が未認証だと連携できない**。その場合は worktree 作成を続行しつつ
  `linear_issue_id` を null にするので、`/status` の乖離検出に現れる (黙って無かったことにしない)
- commit メッセージの `(ELM-xxx)` 規約は**依然として運用されていない**。本 ADR では触らない

### 将来の検討事項
- 移行期が終わったら、commit 規約を CI で強制するか再検討する
- Linear 側からの棚卸し (放置 Issue の検出) を `/linear-status` に持たせるか検討する
