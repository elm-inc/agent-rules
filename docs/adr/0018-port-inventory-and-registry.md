# ADR-0018: ポートは「実態からの逆引き + 任意の予約台帳」で管理する

## ステータス

採択 (2026-08-19)

## 文脈

複数案件を 1 台のマシンで並行開発しており、「どの案件がどのポートか」を人間が覚えていられない。実測 (2026-08-19):

- **LISTEN 110 件 / 稼働コンテナ 40 個 / `~/repos` 配下 92 リポジトリ**
- `ss -tlnp` で**プロセス名が取れるのは 14 件だけ**。残り 96 件は root 所有の `docker-proxy` なので、`ss` 単独では **9 割が「誰のポートか不明」**になる
- 一方 docker compose はコンテナに `com.docker.compose.project.working_dir` ラベルを付けており、**repo の絶対パスが確定で取れる**
- 素の dev server (vite/next) は `/proc/<pid>/cwd` から git root を辿れる
- ポート宣言は `${AINAVICE_DB_PORT:-55433}` のように**環境変数 + 既定値**で書かれることが多く、実効値は `.env` 次第

「ポートを覚えておく」ための台帳を先に作る発想もあるが、台帳は放っておくと実態からズレる。実態が常に正であり、台帳は**実態と突き合わせて初めて価値が出る**。

## 決定

`/ports` スキル + `scripts/port-inventory.py` を置き、**実態からの逆引きを一次情報、予約台帳を任意の補助**とする。

### 1. 3 つの情報源を突き合わせる

| 情報源 | 得られるもの | 確度 |
|---|---|---|
| docker compose ラベル | ホスト公開ポート → repo 絶対パス | 確定 |
| `ss` + `/proc/<pid>/cwd` | 素の dev server → git root | 確定 |
| 設定スキャン (compose/vite/package.json/.env) | 停止中の案件が使う予定のポート | best-effort |

worktree で動いていても案件名がブレないよう、`git rev-parse --git-common-dir` からメインワークツリーを復元して案件名とする。

### 2. 宣言は「バインド」と「ヒント」を区別する

- **bind**: compose の `ports:` ホスト側 / vite の `server.port` / `--port` — 起動時にホストのポートを実際に確保する
- **hint**: `.env` の `*PORT=` — 多くは**接続先**であって確保ではない (`DB_PORT=5432` は docker ネットワーク内の postgres を指すだけ)

**衝突判定に使うのは bind だけ**。ここを混ぜると 5432/3306/6379 が全案件で誤検出になる (実測: 区別前は ERROR 60 件、区別後は実際に起動を妨げるものだけ)。

### 3. 衝突検出は「いま起動できない案件」に畳む

「複数案件が同じポートを宣言している」は**同時に起動しなければ無害**なので ERROR にしない。実際に手が止まるのは「起動しようとした案件が、既に埋まっているポートを要求する」ときだけ。よって:

- 引数なし → 案件ごとに 1 行 (`atlas はいま起動できない — 3000, 5432, 9000 を … が使用中`)
- 案件名あり → その案件が今起動できるかを詳細に答え、駄目なら **exit 1** (fail-close)

### 4. 予約台帳は repo に置かない

案件ごとの確保を宣言する台帳 `~/.config/agent-rules/ports.yml` は**任意**。あれば「確保の重複」「宣言外の占有」「未登録の占有」を検査する。

確保は **連続帯 (`range`) と明示ポート列 (`ports`) の両方**を受ける。実測すると 17 案件中 12 案件は「web=3000 / db=5432」の慣用ポートを使っており**連続帯にまとまらない**。帯しか書けない台帳は、既存案件の大半で使えず「新規案件だけの仕組み」になってしまう。

**agent-rules は public repo であり、案件名には機密顧客案件が含まれる**。台帳を repo に置くと案件名が公開される。`docs/notes/promotion-candidates.md` を gitignore にしたのと同じ理由で、台帳はマシンローカルに置く (別マシンへ持っていくなら private な dotfiles で同期する)。

### 5. 情報源が欠けたら成功扱いにしない

`docker` や `ss` が使えないと live が 0 件になり、素朴に実装すると「衝突なし・exit 0」を返す。これは検知機構が壊れたときに黙って通す典型なので、欠落理由を必ず表示し、`check` は **exit 1** で返す。解析ロジックは `scripts/test-port-inventory.py` で固定し、CI (`port-inventory-test.yml`) で fail-close の挙動ごと検証する。

## 理由

- **台帳ファーストにしない**: 台帳は必ず実態からズレる。実態を一次情報に据えれば、台帳が空でもツールは完全に機能し、台帳は「あると追加の検査が効く」位置づけになる (同期ズレが原理的に事故にならない)
- **docker ラベルが決定打**: 9 割が root 所有で attribution 不能という実測がある以上、`ss` だけの実装では役に立たない。compose ラベルの突き合わせが本体
- **ノイズは機能の敵**: 60 件の ERROR は 0 件と同じ価値しかない。判定の粒度 (bind/hint・案件単位への集約) こそがこのツールの設計

## 検討した代替案

- **台帳のみ (宣言駆動)**: 案件ごとにポートを台帳で予約し、それを正とする。→ 実態と乖離したときに気づけない。既存 92 リポの棚卸しコストも高い
- **`lsof`/`netstat` を都度叩く運用 (ツール無し)**: 現に今それで困っている。root 所有問題があるため素の出力では案件が分からない
- **案件ごとにポート帯を強制する規約 (ツール無し)**: 規約は破られる。機械検証が無い規約は ADR-0015 で得た教訓どおりドリフトする

## 影響

- ポート帯の運用が明文化できる (既に `olly-*` は 13xxx、`ainavice` は 5xxxx と暗黙の帯運用がある)。台帳に書けば逸脱が検出される
- 台帳はマシンごとに独立する。複数マシンで同じ帯を使いたい場合は利用者が同期する必要がある
- 設定スキャンは best-effort であり、動的にポートを決めるアプリ (ランダム割当・オーケストレータ経由) は宣言側に出てこない。live 側では捕捉される
