# ADR-0009: ドキュメントのひな形を実ドキュメントから分離する

## ステータス

採択 (2026-07-01)

## 文脈

`templates/docs/` を単一ソースとし、`/docs-init` が各プロジェクトの `docs/` にドキュメント基盤 (ADR / architecture / design) を展開する運用 (ADR-0003 で確立した in-repo Markdown 方針の一部) を採ってきた。ここで 2 つの問題が顕在化した。

1. **ひな形と実ドキュメントの混在**: ADR の空フォームが `0000-template.md` という名前で `docs/adr/` に展開され、実 ADR (`0001-*.md` …) と同じディレクトリ・同じ連番命名の列に並んでいた。連番 `0000` を名乗るため「ADR 第 0 号」に見え、人間も AI も名前だけでは「ひな形か中身か」を判別できない。誤読・誤編集・誤って連番として数える事故のリスクがある。
2. **テンプレ由来マーカーの漏洩**: `templates/docs/README.md` のタイトルが `# Documentation (テンプレ)` で、`/docs-init` がこれを verbatim コピーするため、実プロジェクトの `docs/README.md` まで「(テンプレ)」と名乗っていた。
3. **幽霊参照**: `architecture/README.md` が存在しない `/docs-sync` スキルを案内していた。

あわせて「オフショア人材向けに日本語・英語の両方でドキュメントを提供したい」という要望があり、当初は `docs/ja/` `docs/en/` の言語ディレクトリ分割を検討した。

## 決定

- **ひな形 (空フォーム) は `docs/_templates/` メタディレクトリに隔離する。** ADR の空フォームは `docs/_templates/adr.md` とし、`docs/adr/` の実ドキュメント列には置かない。
- **命名規約: `_` 接頭辞ディレクトリ = メタ / それ以外 = 中身。**
  - メタ (`_templates/` 配下): 記入用ひな形やリファレンス。`/docs-init` が agent-rules 単一ソースから**毎回上書き同期**する (ユーザーが書き換える対象ではない)。
  - 中身 (連番・通常名: `adr/0001-*.md`, `design/*.md` 等): 人間が書いたドキュメント本体。`/docs-init` は**既存を上書きしない** (`--force` 時のみ)。
- **多言語 (JA/EN ディレクトリ分割) は採用しない** (下記代替案 C)。
- 付随修正: `README.md` の「(テンプレ)」漏洩を解消 (テンプレ由来は HTML コメントに退避)、幽霊参照 `/docs-sync` を実在する `/docs-visualize --force` に置換。
- スキル追従: `/docs-init` は新レイアウトとメタ/中身の上書きポリシーを反映。`/adr-new` はひな形参照先を `_templates/adr.md` に (ローカル → agent-rules 正本のフォールバック順)。

## 理由

- **判別性はパスで担保するのが最も堅い**。ファイル名やディレクトリ名という常に目に入る場所で「メタか中身か」が確定するので、README を読まなくても誤認しない。`_` 接頭辞は Jekyll `_layouts` / SCSS partial / Python dunder 等で広く「単体では成立しない補助物」を意味する既知の慣習で、学習コストが低い。
- **メタ/中身で上書きポリシーを変える**ことで、ひな形は単一ソースに追従して drift せず、人間の成果物は保護される、を両立できる。
- 連番 `0000` を廃することで「ADR 第 0 号」の誤読と、採番グロブへの巻き込みリスクを構造的に消せる。

## 検討した代替案

### 代替案 A: `docs/adr/_template.md` (種別ディレクトリ内に接頭辞付きで残す)
- Pros: ひな形が対応する種別の近くに置ける。変更が最小。
- Cons: 結局 `docs/adr/` の一覧に並ぶため「並んでいる」という元の不満を完全には解消しない。
- 不採用理由: ユーザーの主訴が「実ドキュメントと並んで誤認する」ことなので、物理的に別ディレクトリへ出す方が要件に忠実。

### 代替案 B: ローカルコピーを廃し agent-rules 正本のみ参照
- Pros: 重複ゼロ。drift の余地なし。
- Cons: Claude Code / agent-rules を持たない人 (プロジェクト単独 clone、オフショア等) が手動で ADR 形式を参照できない。
- 不採用理由: 手動作成の参照価値を残しつつ drift も防ぎたい。「メタは毎回上書き同期」で重複の弊害 (drift) は消えるため、ローカルに置く不利益がない。

### 代替案 C: 多言語ディレクトリ分割 (`docs/ja/` `docs/en/`)
- Pros: オフショア人材に英語ツリーを丸ごと渡せる。分離が明確。
- Cons: 全ドキュメント・Mermaid ラベル・README を二言語で維持する**二重保守**が発生し、翻訳は確実に陳腐化 (drift) する。immutable な ADR を両言語で維持する規律も重い。
- 不採用理由: 「提供したいことがある」= 常時全訳ではない。常設の二言語ツリーはコストが便益を上回る。英語ニーズは「引き渡し時にその場で翻訳生成し永続化しない」で二重化なしに満たせる (保存しないから drift しない)。将来スキル化を検討。

## 帰結

### Pros
- ひな形か実ドキュメントか、何がメタかが、パスを見た瞬間に判別できる。
- ひな形は単一ソースに追従、人間の成果物は保護、を上書きポリシーで両立。
- 二重保守を持ち込まずに済む。

### Cons
- `templates/docs/` 内に `_templates/` が入る形になり、「テンプレの中のテンプレ」という命名の入れ子がやや紛らわしい (README で意図を明示して緩和)。
- 既に旧レイアウトで `docs/` を展開済みのプロジェクトは、`0000-template.md` の手動移動が必要 (`/docs-init` 再実行では中身側を上書きしないため)。

### 実機検証 / 将来の検討事項
- 既存プロジェクトの移行手順 (`0000-template.md` → `_templates/adr.md`) を `/docs-init` に自動検出・移行させるか要検討。
- オフショア向けオンデマンド翻訳 (永続化しない英訳生成) のスキル化。
- `/docs-sync` 相当 (図・翻訳の drift 検出) を将来スキルとして実装するか。
