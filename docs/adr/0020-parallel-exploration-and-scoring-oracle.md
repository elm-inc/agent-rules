# ADR-0020: 独立競合探索を条件付きで解禁し、評価関数を前提条件として置く

## ステータス

採択 (2026-09-06)

**ADR-0006 も ADR-0010 も Supersede しない。**どちらも決定は有効で、本 ADR は
**適用範囲を条件分岐させる**だけである (ADR-0019 が ADR-0010 に対して取ったのと同じ形)。

## 文脈

モデル能力の向上により、**人間 1 人が critical path に居座ること**が生産性の律速になった。
以前は A/B の 2 案しか検証できなかったが、いまは 10 案検証しても作業コストが大きく変わらない。
「10 案をどう設計し何を検証するか」を含めて委譲し、監視・検証を独立に走らせたい、という要求が出た。

調査の結果、この要求は**半分は成立し、半分は原理的に成立しない**ことが分かった。

### 成立しないほう: 検証の並列化

[Nine Judges, Two Effective Votes](https://arxiv.org/abs/2605.29800) (2026-05 /
[Apple ML Research](https://machinelearning.apple.com/research/correlated-llm-evaluation-panels))
は、7 モデルファミリー・9 個のフロンティア LLM で審査パネルを構成し、次を示した:

- 実効的な独立票は **約 2 票分**。名目上の独立性の **約 3/4 が消失**
- パネル精度は独立投票の理論値より **8-22 ポイント低い**
- **最良の単一審査者がパネル全体と同等かそれ以上**
- **審査者を増やしても集約を賢くしても直らない** (既存手法はギャップの最大 11% しか埋めない)
- prompt 変種・temperature・CoT・pairwise preference でも頑健

つまり「N 案を N 個の AI に検証させる」は原理的に効かない。
これは ADR-0017 が論文以前に到達していた結論 (「多エージェント検証は全部 Claude なので
groupthink を原理的に解けない」「異ベンダーは常時 1 つまで」) と一致し、本リポジトリの実測
(仕込みバグ 6 件で linter 3/6・LLM 5/6・**和集合 6/6**) とも整合する。
和集合が効いたのは意見が 2 つあったからではなく、**静的解析と意味推論という別種の機構**だったため。

### 成立するほう: 生成の並列化

[AlphaEvolve](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)
(FunSearch の一般化) は LLM + **自動評価器** + 進化ループで実成果を出している。
繰り返し指摘されているのは**評価器の品質が成否を決める**という点。

### 本リポジトリの穴

`templates/docs/design/README.md` の受け入れ基準は**散文**で、適合判定は `/gemini-review` = **LLM 判定**。
N=2 なら人が読めるが、**N=10 を機械的に順位付けするには実行可能な採点関数が要る**。
一方で「評価器を評価する道具」は既にある — `/mutation-check` (変異注入でテストの検出力を測る)。
これは意見ではなく**機構**で検証するため、上記の相関誤りの罠に落ちない。

### ADR-0006 との衝突

ADR-0006 は「並列分解は最大 5、>10 は無益 (サブエージェント多用はトークン約 7 倍)」と定めている。
今回の要求はこれと正面から衝突するように見えるが、**適用範囲が違う**。

## 決定

### 1. 並列化を 2 種類に分け、規律を分岐させる

| 種別 | 内容 | 上限 | 根拠 |
|---|---|---|---|
| **協調的分解** | 1 タスクを分割し、エージェント間で文脈を共有する。調整コストが効く | **最大 5** (ADR-0006 のまま) | 調整コストとトークン増 (約 7 倍) |
| **独立競合探索** | 同一ゴールに N 個の独立解を作り、**機械的に選抜**する。エージェント間の調整は無い | **採点関数が健全なら N を上げてよい** | 調整が存在しないので ADR-0006 の理屈が適用されない |

**「独立競合探索」を名乗れる条件** (全て満たすこと):

- アーム間で文脈・成果物を共有しない (worktree で分離)
- 選抜が**実行可能な採点関数**で機械的に行われる (人間や LLM の講評で選ばない)
- **アームの分散が approach レベルである** (同一モデル・同一プロンプトの seed 違いは相関して
  実効アーム数が減るため、独立競合探索とは呼ばない)。
  **「approach 分散」は主観的で名乗るだけの抜け道になりうるため、事後に測る**:
  アーム間の成果物の類似度 (差分の Jaccard 係数) の中央値が **0.7 を超えたら
  実質同一アプローチとみなし N を減らす**

### 2. 評価関数を前提条件 (gate) として置く

**Stage 1 (実行可能な採点関数) を満たさないタスクでは、独立競合探索を行わない。**

採点関数は JSON でスコアを返し、**採点関数自体が攻略に耐えることを数値で確認する**ことを
完了条件とする。合否は次で決め、**1 つでも満たさなければ独立競合探索を行わない**:

| 項目 | 合格条件 |
|---|---|
| 既知の悪い実装 (2-3 個) | 全て下位に落ちる |
| **敵対的エージェント (2 個以上)** | **上位に 1 つも入らない** |
| `/mutation-check` の生存変異率 | **10% 以下** |
| 採点の再現性 | 同一実装を 3 回採点してスコアが一致 |

「既知の悪い実装を落とせるか」だけでは**固定サンプルへの識別力**しか測れず、
N 並列 + 自律ループという**強い最適化圧に対する頑健性**を測っていない。
それでは得られるのが「最良の実装」ではなく「**採点関数を最も上手く攻略した実装**」になる。
人間が上位数件しか読まない前提では、攻略成功案は回収されない。

**落とせないなら並列化しない。** 順位がノイズになるだけで、10 倍のコストを払って
10 個の候補を人間が読むという、現状より悪い状態になる。

### 3. 検証層は「数」ではなく「機構の異種性」で強くする

ADR-0017 の「異ベンダーは常時 1 つまで」を**維持・強化する**。
N 案を検証するために審査 LLM を N 個並べることを**禁止する**。

検証の強化は次の軸でのみ行う: 機械的検査 (lint/型/semgrep) / 実行による観測 (テスト・ベンチ・E2E) /
変異注入 (`/mutation-check`) / 異ベンダー 1 つ (ADR-0019 の高リスク時は Astra)。

### 4. 無人実行では予算を hard cap にする

ADR-0010 は「予算超過でもブロックしない (人手ゲート)」と決めた。
**この決定は「人間が起動する場合」の規律であり、無人実行では成立しない。**

- **人間起動** (`/fable-task` 等): ADR-0010 のまま。ソフトゲート、ブロックしない
- **無人実行** (Routines / `/loop` / Workflow の自律ループ): **hard cap で停止する**

理由: ADR-0010 が「ブロックしない」を選んだのは「予算超過を理由に高リスク変更の最終レビューが
自動で止まると本末転倒」だから。**この論理は人間がその場にいて判断できることが前提**である。
無人実行では判断者が居らず、公表事例では 4 エージェントのループが 11 日間走って **$47,000**、
CloudFormation の重複起動で **$6,531** の実害が出ている。

### 5. 自律実行の権限を構造的に制限する

`bypassPermissions` は次を**全て**満たすタスクにのみ許可する:

- worktree の外に書き込めない
- 課金 API を叩かない
- 本番環境に触れない

Step Finance の事例 (AI エージェントに人間承認なしの送金権限を与え **$27-30M** の損失) は
権限モデルの設計ミスであり、モデルの賢さでは防げない。

### 6. 採点対象を封印する (隠蔽は採らない)

reward hacking は **15.4% の failure mode rate** として観測されている。
当初は「採点ロジックを実装エージェントから隠す」ことを決定に含めたが、**これは成立しない**。

> **2026-09-06 に実証**: 同一リポジトリに採点スクリプトを置く限り、`cat` でも
> `git show HEAD:<path>` でも `git grep` でも読める。Read 権限を path 単位で拒否しても
> Bash 経由で漏れる。さらに実装エージェントはテスト・ベンチを**実行する必要がある**ため、
> スコアの構成要素に必然的に触れる。

したがって守り方を**秘匿から改変不能性へ**変える:

- 採点に使うテスト・ベンチは**アームの作業ツリーから取らない**。封印領域 (`sealed/`) に置き、
  アームからは read-only にする
- 採点は**アームの外のプロセス**が実行する
- これにより「テストを削る・弱める」「`# noqa` を足す」「ベンチ対象を縮小する」は
  **構造的に不可能**になる (規律ではなく権限で防ぐ)

**残るリスク**: スコア値をアームに返すと oracle query として hill-climbing されうる。
緩和は (a) スコアを返さず一発勝負にする、(b) 返すなら pass/fail のみ、のいずれか。
反復改善させたい場合はこのリスクを引き受けていることを自覚する。

### 7. 測れない指標を 0 で埋めない (採点関数にも ADR-0019 の原則を適用)

採点スクリプトに `|| echo 0` のようなフォールバックを書かない。
ツール未導入・一時障害・flaky を「実力が低い」に変換してしまい、
**環境運が良かったアームが上位に来る**。測れなかった指標は `null` とし、
そのアームは `measurable: false` として**順位から除外し、失格ではなく測定不能として人間に報告する**。

これは ADR-0019 決定 5 (「取れないものを推定で埋めない」) の採点関数への適用である。

### 8. キャリブレーション重み付けは作り込まない

Metaculus は track record 重み付け (Metaculus Prediction) を **2024-11 に廃止**し、
現在の Community Prediction は**単純な recency-weighted median** である (確認済み)。
廃止された Metaculus Prediction は performance weighting と extremization を掛けていた。

> 出典の強さを分けて記す。**「廃止され recency-weighted median に置き換わった」は一次情報で確認済み**
> ([Metaculus FAQ](https://www.metaculus.com/faq/))。
> 一方「Brier 0.107 (重み付け) vs 0.108 (単純 median) でほぼ差が無かった」という**具体値は二次情報**
> ([EA Forum の集約手法まとめ](https://forum.nunosempere.com/posts/acREnv2Z5h4Fr5NWz/my-current-best-guess-on-how-to-aggregate-forecasts))
> であり、本 ADR では**未検証の補強材料**として扱う。決定の根拠は具体値ではなく
> 「Metaculus 自身が精緻な重み付けをやめて単純な median に戻した」という事実の方に置く。

較正台帳は「どの層が最近何も捕まえていないか」が見える程度に留め、重み関数は実装しない。
これは ADR-0017 の「層を減らすほど各層が実行される」と整合する。

## レッドチーム指摘への対応 (`/deepseek-redteam`, 2026-09-06)

本 ADR と設計ドキュメントを起草直後にレッドチームへかけ、**Critical 2 件で設計を作り直した**。

| 指摘 | 致命度 | 判定 | 対応 |
|---|---|---|---|
| **Goodhart 則の経路が塞げていない**。Stage 1 の検証は固定サンプルへの識別力だけで、最適化圧への敵対的頑健性を測っていない。得られるのは「最良の実装」ではなく「採点関数を最も上手く攻略した実装」 | Critical | ✅ 妥当 | **決定 2 を改訂**。敵対的エージェント 2 個以上が上位に入らないことを合格条件に**必須化**。mutation 生存率 10% 以下・再現性も数値で固定 |
| **「採点ロジックを隠す」は同一リポジトリでは物理的に成立しない**。`cat` / `git show` / `git grep` で読める。実装エージェントはテスト・ベンチを実行する必要があり、構成要素に必然的に触れる | Critical | ✅ **妥当 (実証済み)** | **決定 6 を全面差し替え**。隠蔽を放棄し、`sealed/` による**改変不能性**に変更。テスト・ベンチをアームの作業ツリーから取らない構造にした |
| 採点スクリプトの `\|\| echo 0` フォールバックが、ツール障害を「実力の低さ」に変換する。環境運が良いアームが上位に来る | High | ✅ 妥当・**自己矛盾だった** | **決定 7 を新設**。ADR-0019 の「測れないものを 0 と偽らない」を採点関数にも適用。`measurable:false` で順位から除外 |
| 性能指標が N アーム並列実行中の CPU/IO 競合で汚染される。worktree 分離はファイルしか分けない | High | ✅ 妥当 | 設計に追記。性能を採点に含めるフェーズは**直列化**するか専用資源を割り当てる |
| 「approach 分散」が主観的で、名乗るだけで N を増やす抜け道になる | High | ✅ 妥当 | **決定 1 に測定可能な判定基準を追加**。アーム間類似度 (Jaccard) の中央値 > 0.7 なら実質同一とみなし N を減らす |
| `/mutation-check` の生存変異率が「記録する」だけで合否閾値が無い | High | ✅ 妥当 | 10% 以下を合格条件として明記 |
| Stage 1 の gate が「だいたい動くから通そう」で形骸化する | High | ✅ 妥当 | 合否を**全て数値**にした (上表)。主観判断の余地を残さない |
| hard cap は API 課金の遅延があるため請求を完全には止められない | Medium | ✅ 妥当 | 設計の「引き受けるリスク」に明記。cap は「暴走を数時間で止める」装置であって上限保証ではない |
| 採点関数のバージョン管理が無いと過去の順位と比較できず較正台帳が無意味になる | Medium | ✅ 妥当 | 設計に追記。スコアに採点関数の commit を併記する |
| 採点器をリポジトリから分離した別サービスにすべき | Medium | ⚠️ 部分採用 | 現規模には過剰。`sealed/` + アーム外プロセスで同等の改変不能性を得る。**将来サービス化する余地は残す** |
| 採点を ranking ではなく filter (pass/not pass) として使い、最終判断は人間が行う | Medium | ⚠️ 条件付き採用 | 本 ADR の目的 (人間を critical path から外す) と正面から衝突するため全面採用はしない。ただし**敵対的ゲートを通過していない段階では filter として使う**運用を推奨する |

> **1 点だけ直すなら**としてレッドチームが挙げたのは
> 「隠すのをやめ、採点器を分離し、敵対的エージェントが上位に入らないことを Stage 1 の必須条件にせよ」。
> **これを決定 2 と決定 6 として採用した。**

## 理由

- **検証の並列化が効かないことが実証された以上、そこに投資しないのが最大の節約**。
  素朴に 10 審査者を並べると、9 個並べて 2 個分の情報しか得られない
- **ボトルネックは「AI が待つこと」ではなく「人間が全ループの critical path に居ること」**。
  外すべきは判定そのものではなく、判定を受けて次を指示する部分
- **順序が本質**。採点関数が無い状態での並列化は状況を悪化させるため、gate として置く
- **失敗の質が変わる**。silent failure (壊れても self-report は "operational") が観測されており、
  無人実行では「止まらない」ことが最大のリスクになる。本リポジトリは `frontier-usage.sh` で
  既に「測れないものを 0 と偽らない」を実装済みで、その原則を全計器に広げるのが自然

## 検討した代替案

### 代替案 A: 審査 LLM を N 個並べて多数決で選抜する
- Pros: 実装が単純。採点関数を書かなくてよい
- Cons: **原理的に効かない** (§文脈)。9 個で 2 個分、最良の単一審査者以下になることもある
- 不採用理由: 実証済みの負の結果がある

### 代替案 B: ADR-0006 を Supersede して「並列は無制限」にする
- Cons: 協調的分解でのトークン約 7 倍という根拠は今も有効。無条件解禁は事故を招く
- 不採用理由: 2 つの並列化は別物なので、条件分岐が正しい表現

### 代替案 C: 採点関数なしで N 案を出し、人間が読んで選ぶ
- Cons: **これが現状より悪い**。人間の読む量が N 倍になり、critical path がむしろ太る
- 不採用理由: 解こうとしている問題を悪化させる

### 代替案 D: 無人実行でもソフトゲートのまま (ADR-0010 を全面適用)
- Cons: 判断者が居ない。$47,000 / 11 日の事例が示すとおり、誰も気づかない
- 不採用理由: ADR-0010 の「ブロックしない」判断は人間の在席が前提

## 帰結

### Pros
- 「検証を並列化する」という**効かない投資を事前に排除**できる
- 並列化の可否が採点関数の有無で機械的に決まり、判断コストが下がる
- ADR-0006 / ADR-0010 を壊さずに適用範囲を明確化できる

### Cons / 限界
- **採点関数を書けないタスクは並列化の対象外**になる (UI の良さ、ドキュメントの分かりやすさ、
  設計の妥当性など)。「何でも並列化できる」わけではない
- **採点関数の設計コストが高い場合は割に合わない**。1 回きりのタスクでは
  採点関数を書く時間 > 10 案から選ぶ時間 になりうる。反復するタスクに限定する
- **Stage 1 の実証が失敗する可能性がある**。その場合「本リポジトリの仕事は独立競合探索に向かない」が
  結論になる。これも価値のある結果として受け入れる
- 無人実行の hard cap は、必要な処理を途中で止めうる。ADR-0010 が避けたかった
  「コスト都合で品質ガードが外れる」問題が、無人実行では別の形で戻ってくる
- **hard cap は請求の上限を保証しない**。API 課金の反映に遅延があるため、cap 到達で停止しても
  実際の請求はさらに積まれうる。「暴走を数時間で止める」装置として理解する
- **封印しても、スコア値を返す限り hill-climbing の余地は残る**。完全に塞ぐには
  アームにスコアを返さない (一発勝負) しかなく、反復改善と両立しない
