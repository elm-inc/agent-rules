# ADR-0023: ハーネス構成 — 宣言ファイル (.harness.yml)・2 チャネル配布・外部送信は遮断せず検知と通知

## ステータス

採択 (2026-09-18)

## 文脈

agent-rules は実質的に elm-inc の「ハーネス」(モデルの外側にある文脈・ツール・ガードレール・フィードバック・検証) である。要求は、**標準化・共通化を進めつつ、プロダクトごとの固有事情に適切に対応し、開発のタスクやワークフローを安定運用すること**。

2026-09-18 にローカル clone 約 75 リポを実測したところ、次のことが分かった (詳細: [docs/design/harness-architecture.md](../design/harness-architecture.md) §1-1):

- 標準化は L1 (symlink 配布の CLAUDE.md・RULES.md・スキル) でだけ届いており、`.claude/settings.json` を持つ案件は約 9 件、Claude 関連ファイルが一切無い案件が 40 件。**プロダクト固有の事情を機械可読に置く場所が無い**
- 機密案件で外部 LLM への送信を止める手段は「実行時に API キーを空にする」非常口だけで、どのリポが機密かの記録も無い。**人が忘れれば、誰も気づかないまま送信される**
- 案件固有の目印 (`.no-linear`・`.newrelic-profile`・提案中だった `.stack.yml`) が個別に増えている
- 全資産が main から即時配布され、版の固定ができない。また `install.sh --fix` はトップレベルのキー単位の add-only マージなので、`hooks` を既に持つマシンに新しい hook を配れない

設計は Fable 5.1 のレビューを受けた。当初案は送信を hook で遮断するものだったが、**実測で本リポの実際の送信を 8 件中 0 件しか検出できず**、ユーザー入力のスラッシュコマンドでは hook が発火しないことも分かった。遮断を成立させるには回避経路の列挙が際限なく広がる。これを受けてユーザーが脅威モデルを絞った。

## 決定

1. **ハーネスを「4 種の構成要素 × 3 層」で扱う**
   - 構成要素: Guides (事前に導く) / Sensors (検知して伝える) / Gates (機械的に止める) / Meters (ハーネス自体を監視する)。Böckeler の Guides・Sensors に、本リポが既に依存している Gates・Meters を加えた
   - 層: Core (全案件) / Profile (案件名でなく特性で選ぶ部品: 機密区分・スタック・モジュール) / Local (プロダクト固有)。ADR-0013 の L1/L2/L3 を拡張し、Local を機械可読にする
2. **プロダクト固有の宣言は `.harness.yml` に一本化する**
   - repo ルート、または repo に置けない場合はローカル宣言 `~/.config/agent-rules/harness/<host>/<org>/<repo>.yml`
   - 機密区分は**両者のうち厳しい方**を採る (上流の変更で区分が下がらない)。未宣言は confidential と同じに扱う。読めない場合は「判定不能」として伝える
   - stack-governance の宣言は `.stack.yml` を作らず、`stack:` セクションにする。版の pin は `pin:` (ハーネス本体) と `stack.radar:` (radar) の 2 本
3. **配布は 2 チャネル (+ コピー)**
   - 即時: CLAUDE.md・RULES.md・ユーザーレベル hook・送信ヘルパ・台帳 (symlink)
   - 版固定: スキル本文・agent・Profile (Claude Code plugin)。前提 4 点 (案件別 pin の可否・scripts の同梱・名前空間・Codex との非対称) を実機で解消するまで移行しない
   - `.claude/rules` 雛形は `/project-init` のコピー
4. **外部 LLM への送信は遮断せず、検知して送信前に伝える**
   - 脅威モデルは「Claude Code の通常の利用でのうっかり送信」に限る。意図的な持ち出し・改ざん・ネットワーク分離は対象外
   - 検知は hook ではなく**送信ヘルパ** (`curl-secret.sh`・`nano_banana.py`・`codex-astra.sh`・新設の `codex-run.sh`) と、送信するスキルの事前チェック手順に置く
   - 警告の対象: confidential と未宣言ではローカル LLM 以外すべて。internal では DeepSeek だけ。台帳 `config/egress.yml` が単一ソース
   - 警告件数・判定不能件数・未宣言 repo 数を `/status` に出す。送信がすべてヘルパを通っていることを CI のコーパス試験で機械検査する

## 理由

- **遮断より検知を既定にする**: システムで強く規制すると、開発以前に作業が止まる (ユーザー判断)。加えて、遮断は回避経路の列挙競争になり、それ自体が保守負債になる。うっかり送信には「送信前に伝える」で足りる
- **検知を送信ヘルパに置く**: 呼ばれ方 (ユーザー入力・モデルの判断・サブエージェント・Codex) に関係なく同じ判定になる。新しい hook が要らないので、配布の欠陥 (トップレベルキー単位のマージ) にも依存しない
- **Sensor は黙って止まってはいけない**: 判定不能を public に倒すと、壊れたときに黙って送信される。frontier-usage の jq abort で予算ガードが 10 倍過少報告した事故と同型
- **宣言を 1 ファイルにする**: 目印が増えるほど、どれを見ればよいかが分散する。Profile を特性で選ぶことで、public repo に案件名を出さずに済む (ADR-0018・ADR-0021 と同じ理由)
- **2 チャネルにする**: 安全や検知の修正を 75 件の PR 待ちにしない一方、スキルの挙動変更は案件ごとに受け入れを制御したい。plugin では CLAUDE.md・rules を配れないため、即時チャネルは symlink のまま残る
- **pin を 2 本にする**: radar の閾値変更の受け入れ (案件 CI が読む) とハーネスの版上げ (Claude Code が読む) は、読み手も更新頻度も違う

## 検討した代替案

### 代替案 A: 送信を遮断する (hook の deny・許可リスト方式)
- Pros: 送信そのものを防げる
- Cons: 本リポの送信形態 (関数・継続行) を hook では検出できず、回避経路の列挙が際限なく広がる
- 不採用理由: ユーザー判断 (作業が止まる)。上記の保守負債

### 代替案 B: ネットワーク分離 (`bwrap --unshare-net` + 許可リスト proxy)
- Pros: 意図的な持ち出しまで構造的に塞げる唯一の手段
- 不採用理由: 脅威モデルの対象外で、遮断でもある。必要になったら再検討する

### 代替案 C: 宣言を中央の台帳 (agent-rules) に集約する
- 不採用理由: 案件名が public repo に出る

### 代替案 D: 現状維持 (区分をスキルの引数・環境変数で都度指定する)
- 不採用理由: 人が忘れた時点で、誰も気づかないまま送信される

## 帰結

### Pros
- 機密の区分が機械可読になり、送信の前に必ず伝えられる
- 案件固有の目印が 1 ファイルに集まる
- ハーネスの変更の影響範囲を、案件ごとに制御できる道筋ができる

### Cons
- 検知であって防止ではない。警告を見落とせば送信される
- ヘルパを経由しない送信 (手書きの `curl`・MCP・Chrome 等) は検知できない。前者は CI のコーパス試験で本リポ内の増加を防ぎ、MCP は Phase 4 で検討する
- 未宣言の repo が多いうちは警告が多い。初回の `/harness-audit` で区分を一括で付ける運用が要る

### 実機検証 / 将来の検討事項
- plugin の案件別 pin (`pluginVersions` の可否は情報源で回答が割れている)・名前空間・Codex との非対称 — Phase 3 の関門
- `install.sh` を hook entry 単位の add-only マージに直す — hook を足す前に必須
- 既存 `claude-guard.sh` の Figma ルールが継続行の curl をすり抜ける (Fable の実測で判明した既存バグ)
